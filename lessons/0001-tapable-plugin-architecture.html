第 1 课 · 插件架构与 tapable：核心库如何做到"不认识"它的插件

Lesson 0001 · 预计 20 分钟 · 配套速查：tapable 速查表

本课目标：看完后你能回答——这个项目里"自动开聊核心流程"和"落库/钉钉通知"是谁也不依赖谁的两个模块，它们靠什么协作？以及：让你手写一个带插件系统的核心库，你的第一行代码该写什么？

1. 先看一个奇怪的依赖方向

打开核心库的 package.json（packages/geek-auto-start-chat-with-boss/package.json），它的依赖里没有 sqlite-plugin，也没有 dingtalk-plugin——虽然主流程运行中明明在往数据库写开聊记录、在发钉钉通知。

反过来，packages/sqlite-plugin 和 packages/dingtalk-plugin 也不 import 核心库。

两边互不认识，事情却发生了。这不是巧合，是本课的主角：控制反转（IoC）+ 事件钩子（hooks）。依赖方向不是"核心 → 插件"，而是"组装者 → 双方"：

组装者 run-core/main.mjs
 ├─ import 核心库 mainLoop ──── 传入 hooks
 └─ import 插件 apply(hooks) ── 挂上回调

为什么要费这个劲？想象两条运行形态：无 GUI 的 pnpm start（run-core 组装）和 Electron 桌面版（UI 包组装，另加截图等插件）。核心库写死任何一个插件，另一种形态就带上了用不上的依赖——插件化让"同一核心、多种组装"成为一行配置的事。

2. 三种角色与真实代码

角色 A · 定义方：组装者声明 18 个钩子

packages/run-core-of-geek-auto-start-chat-with-boss/main.mjs:48-67（节选）：

const hooks = {
  puppeteerLaunched:   new SyncHook(['browser']),      // 同步：拿到浏览器实例
  pageGotten:          new SyncHook(['page']),         // 同步：拿到页面
  userInfoResponse:    new AsyncSeriesHook(['userInfo']),
  newChatStartup:      new AsyncSeriesHook(['positionInfoDetail', 'chatRunningContext']),
  jobMarkedAsNotSuit:  new AsyncSeriesHook(['jobInfo', 'markContext']),
  matchReportGenerated: new AsyncSeriesHook(['jobInfo', 'matchResult']),  // ← 你写的 AI 匹配就挂这
  errorEncounter:      new SyncHook(['errorInfo']),
  // …共 18 个：11 个 AsyncSeriesHook + 7 个 SyncHook
}
initPlugins(hooks)                        // ← 先让插件挂载
await hooks.daemonInitialized.promise()   // ← 再等"初始化完成"广播

两个要点：构造参数是参数名数组（['jobInfo', 'matchResult']），纯粹为了文档和报错可读，不是默认值；类型选 AsyncSeriesHook 是因为落库这类回调必须按注册顺序串行跑完。

角色 B · 消费方：插件把自己挂上去

Webpack 立下的惯例：插件是一个带 apply(hooks) 方法的类。本项目完整复刻。packages/sqlite-plugin/src/index.ts:102 与 244：

export default class SqlitePlugin {
  constructor(dbFilePath) {
    this.initPromise = initDb(dbFilePath)   // 构造即启动异步建库，不 await
  }
  apply(hooks) {
    hooks.jobMarkedAsNotSuit.tapPromise('SqlitePlugin',
      async (_jobInfo, { markReason, markOp, jobSource } = {}) => {
        const ds = await this.initPromise          // 回调里才等库就绪
        return await saveMarkAsNotSuitRecord(ds, _jobInfo, /* … */)
      })
    hooks.matchReportGenerated.tapPromise('SqlitePlugin',
      async (_jobInfo, matchResult) => {
        const ds = await this.initPromise
        return await saveMatchReport(ds, _jobInfo, this.userInfo, matchResult)
      })
  }
}

钉钉插件则是另一种姿态——自管可用性，不可用就优雅降级（packages/dingtalk-plugin/index.mjs:49-56）：

apply(hooks) {
  if (!this.dingtalkAccessToken) {
    console.log('[DingtalkPlugin] AccessToken is empty, plugin won\'t do anything.')
    return                                   // 不挂任何钩子，核心照常运行
  }
  hooks.newChatStartup.tap('DingtalkPlugin', ({ jobInfo, bossInfo }) => {
    collectedMessageList.push(createTextMessage(/* … */))  // 只入队，定时批量发
  })
}

角色 C · 触发方：核心库在关键时刻"广播"

核心库 packages/geek-auto-start-chat-with-boss/index.mjs:1599（开聊成功后）：

await hooks.newChatStartup?.promise(targetJobData, {
  chatStartupFrom: ChatStartupFrom.AutoFromRecommendList,
  jobSource: JobSource[computedSourceList[currentSourceIndex]?.type]
})

注意 hooks 是 mainLoop(hooks) 传进来的参数——核心库从头到尾不知道谁在听、有几个在听、甚至有没有人在听。await …promise() 这一行就是在说："各位插件，开聊成功了，你们要记的记、要发的发，我等你们办完再走。"

4. 四个值得偷师的细节

  1. apply(hooks) 惯例：来自 Webpack 的 plugin.apply(compiler)。一个动词明确了挂载时机——组装者控制插件何时上线，插件控制自己监听什么。
  2. hooks.matchReportGenerated?.promise() 的可选链（index.mjs:1484）：AI 匹配是后加的新钩子，老调用方可能还传着没有这个字段的旧 hooks 对象。一个 ?. 让核心库对新旧组装者都兼容——演进中的公共 API 该有的样子。
  3. 同一钩子可被同一插件 tap 两次（sqlite-plugin/src/index.ts:221-233：jobDetailIsGetFromRecommendList 连挂两个 tapPromise，一个存职位、一个记在招状态）。钩子是"多播广播"，不是"单播委托"。
  4. initPromise 模式：构造函数里启动异步初始化但不 await，每个回调里 await this.initPromise 再用——初始化一次、处处等待，插件挂载瞬间不会被数据库拖住。

5. 检索练习

别翻回上文，凭记忆作答（答错不要紧，错的地方才值得重读）：

组装者里 new DingtalkPlugin(token).apply(hooks) 这一行，扮演的角色是？

定义在 48-67 行已完成，这一行是把插件挂上去——消费方。触发方在核心库里。

给 AsyncSeriesHook 注册一个 async 函数，该用哪个方法？

tapPromise 注册 Promise 风格回调；promise() 是触发方法——注册用 tap 系，触法用 call 系，别混。tap 只能挂同步函数（AsyncSeriesHook 上挂同步函数也可以，但 async 函数必须 tapPromise）。

SqlitePlugin 与 DingtalkPlugin 都注册了 newChatStartup，核心 await …promise() 后两者的执行方式是？

Series＝串行：先跑完注册早的（SqlitePlugin 在 initPlugins 中先 apply），await promise() 会等最后一个完成。要是落库允许并发，才考虑 AsyncParallelHook。

核心库里写 hooks.matchReportGenerated?.promise(...) 加可选链的原因最可能是？

新钩子刚加入时，旧的组装者（别的 fork、旧版 UI）传入的 hooks 对象可能还没有这个字段——?. 让核心库对"没这个钩子"的调用方也安全运行。语法上并不强制。

6. 实战：去真实代码里走一遍

在仓库里完成三件事（用编辑器打开，别靠记忆）：

  1. 打开 packages/run-core-of-geek-auto-start-chat-with-boss/main.mjs，数出 18 个钩子里 SyncHook 和 AsyncSeriesHook 各几个，并找出哪个钩子的命名暴露了它就是你最近加的 AI 匹配功能。
  2. 全仓搜索 matchReportGenerated，列出：谁 tap 它（文件:行）、谁触发它（文件:行）——一共应有两处触发。
  3. 思考：假如你想"每次点击开聊按钮之前"插入自己的逻辑（比如发一条本地通知），应该 tap 哪个钩子？它和 newChatStartup 的区别是什么？
做完后点开核对答案

① 7 个 SyncHook、11 个 AsyncSeriesHook；AI 匹配的钩子是 matchReportGenerated。

② tap：packages/sqlite-plugin/src/index.ts:256（tapPromise 存报告）；触发：packages/geek-auto-start-chat-with-boss/index.mjs:1484（评估成功，含 null 结果）与 :1492（评估抛错时也存一条 null 记录）。注意第二处触发包在 try/catch 里——插件回调抛错会让 promise() reject，不能让它打断主流程。

③ newChatWillStartup（触发于 index.mjs:1565，在点击按钮之前）。区别：newChatWillStartup 是"将要"开聊（还能在此影响流程），newChatStartup 是"已经"开聊成功（只适合记录与通知）。will/did 命名对是事件系统的常用词汇。
