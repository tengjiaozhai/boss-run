第 2 课 · 数据获取的三个层次：让网站自己把数据送上门

Lesson 0002 · 预计 25 分钟 · 前置：第 1 课 插件架构 · 配套速查：Puppeteer 数据获取速查表

本课目标：理解这个项目所有业务数据（职位列表、详情、开聊结果）没有一行来自 HTML 解析的秘诀——网络层、框架层、DOM 层各管什么、怎么配合。看完后你能为一个陌生的 SPA 网站设计出同样的取数方案，并说清哪层最耐久、哪层最脆弱。

1. 总览：一个"手眼分工"的原则

自动化脚本要跟网页打交道的事情只有两类：操作（点击、滚动、输入）和取数（职位列表、详情、结果）。本项目的原则是：

操作 → 落在 DOM 层（那是"手"，模拟人去点）
取数 → 优先网络层，其次框架层（那是"眼"，听和看，不拆 HTML）

于是形成三层金字塔，越往上保真度越高、越耐改版：

层次原理耐久性本项目取到的数据
① 网络层监听浏览器发出的 XHR 的响应最高（API 不轻易变）职位详情 JSON、开聊结果、用户信息
② 框架层直读页面 Vue 实例的内存状态中（依赖框架实现）职位列表、是否还有更多页、当前选中职位
③ DOM 层选择器 + 文本最低（改版即碎）仅按钮文字确认（"立即沟通"）

2. 网络层的三种姿势

姿势 A · 长期旁听：插件自己收数据

第 1 课埋的伏笔在这：SqlitePlugin 落库的数据从哪来？答案它自己听来的（packages/sqlite-plugin/src/index.ts:103-121）：

hooks.pageGotten.tap('SqlitePlugin', (page) => {
  page.on('response', async (response) => {          // 旁听所有响应
    if (response.url().startsWith('https://www.zhipin.com/wapi/zpgeek/job/detail.json')) {
      const data = await response.json()               // 服务端原始 JSON
      if (data.code === 0) {
        await saveJobInfoFromRecommendPage(ds, data.zpData)  // 直接入库
      }
    }
  })
})

核心库只负责"像人一样点开职位卡片"，BOSS 自己会请求详情 API——插件在网络层顺手截胡。核心库与数据采集互不知晓，这是插件架构真正跑通的关键。

姿势 B · 一次性等待：点击后等这个 API

点击职位卡片后怎么知道详情加载完了？等那个 API 出现（geek-auto-start-chat-with-boss/index.mjs:1138-1148）：

await targetJobElProxy.click()
await page.waitForResponse(response =>
  response.url().startsWith('https://www.zhipin.com/wapi/zpgeek/job/detail.json')
)

顺序铁律：先注册等待，再点击。waitForResponse 只能看到注册之后发生的响应。开聊结果的确认同款（index.mjs:1571-1581，等 friend/add.json 且 URL 里带本职位 jobId）。

姿势 C · 请求-响应对象配对：最精巧的一处

滚动加载下一页时有个难题：滚到底触发的是下一次翻页请求，怎么确认"新数据到了"而不是误把旧响应当新的？URL 会一模一样，按 URL 判断不可靠（index.mjs:909-938）：

page.on('request', function reqHandler (request) {
  if (request.url().startsWith('.../recommend/job/list.json') ||
      request.url().startsWith('.../search/joblist.json')) {
    requestNextPagePromiseWithResolver = …           // 用这个请求对象建一个 promise
    page.off(reqHandler)                              // 立即注销自己
    page.on('response', function resHandler (response) {
      if (response.request() === request) {           // ★ 对象同一性配对
        requestNextPagePromiseWithResolver?.resolve()
        page.off(resHandler)
      }
    })
  }
})

response.request() === request——不比较 URL、不比较时间戳，直接比较对象是不是同一个。Puppeteer 中每个 Request 对象与其派生的 Response 一一关联，对象同一性就是最精确的配对。消费端在滚动循环里（index.mjs:1088-1102）：

while (!requestNextPagePromiseWithResolver && !hasReachLastPage) {
  scrolledHeight += increase                            // 步长 40~70 随机
  await page.mouse.wheel({ deltaY: increase })          // 真滚轮事件
  await sleep(100)
  await requestNextPagePromiseWithResolver?.promise     // 捕获到翻页请求就等它
  hasReachLastPage = await page.evaluate(`
    !(document.querySelector('.page-jobs-main')?.__vue__?.hasMore)`)
}

3. 框架层：直接翻 Vue 的抽屉

BOSS 直聘网页是 Vue 2 写的，Vue 实例会挂在 DOM 元素上（el.__vue__）。本项目四处直读（全部在 index.mjs）：

位置表达式拿到什么
:952.page-jobs-main?.__vue__?.jobList整页职位列表（结构化对象数组）
:1097…__vue__?.hasMore还有没有下一页（决定是否停止滚动）
:1155.job-detail-box.__vue__.data右侧详情面板的完整数据（jobInfo/bossInfo/brandComInfo）
:1156.page-jobs-main.__vue__.currentJob当前选中的是哪个职位（列表与详情对账用）

为什么巧：这些数据网站本来就请求过了、渲染过了，就存在框架实例的内存里。直读意味着零额外请求（不触发风控）、零解析误差（不是字符串是对象）、零重复计算。代价是依赖实现细节——Vue 3 生产构建没有 __vue__，这就是它排在网络层之后的原因。

你写的 AI 匹配评估吃的 targetJobData（jobInfo/bossInfo/brandComInfo 三段）正是 :1155 那行读出来的——AI 功能的数据源就站在框架层上。

4. DOM 层：只留给"手"和最简确认

全项目对 DOM 文本的读取几乎只剩一处——确认开聊按钮状态（index.mjs:1532-1533）：

const startChatButtonInnerHTML = await page.evaluate(
  'document.querySelector(".job-detail-box .op-btn.op-btn-chat")?.innerHTML.trim()')
if (startChatButtonInnerHTML !== '立即沟通') { /* 已沟通过，跳过 */ }

其余 DOM 操作全是"手"：点击卡片（:1138）、模拟滚轮（:1093）、scrollIntoView 且 block 随机取 center/end（:1122-1128）——连滚动到位的方式都带随机性，这就是第 1 轮聊过的拟人化思想落在 DOM 层的样子。

6. 检索练习

翻页确认为什么用 response.request() === request 而不是比较 URL？

重试、预取、并发请求都可能让同一 URL 出现多次响应；时间戳判断也只能猜。对象配对是唯一能精确锁定"这一次请求的这一次响应"的办法。

page.on('response') 与 page.waitForResponse() 最本质的区别是？

旁听（插件长期落库）用 on；"等某件事发生再继续"（点击后等详情）用 waitForResponse。两者拿到的 Response 对象能力相同。

如果 BOSS 直聘把网页重构为 Vue 3 生产构建（不暴露 __vue__），哪层代码失效？

__vue__ 是 Vue 2 实例暴露；Vue 3 生产构建没有。但 XHR 照发（网络层不变），类名不改的话点击也照常。这就是三层耐久性排序的意义：数据保真度越高的层，对页面形态变化越不敏感。

滚动加载为什么用 page.mouse.wheel() 小步多次，而不是一次 window.scrollTo 跳到底？

scrollTo 是"瞬移"，没有滚轮事件序列，行为特征与人截然不同；wheel 逐格滚动且步长 40~70px 随机，配合 sage-time 的长间歇，整体行为节奏接近真人。

7. 实战：把三层找全

打开 packages/geek-auto-start-chat-with-boss/index.mjs：

  1. 全文件搜索 __vue__，核对 4 处框架层直读（速查表说有 4 处，验证我有没有漏）。
  2. 搜索 waitForResponse，找出全部等待点，并回答：哪两处的谓词除了 URL 还匹配了别的条件？
  3. 思考：职位列表数据为什么走框架层（__vue__.jobList）而不是像详情那样在网络层截获列表 API 的响应？（提示：看 :914-915 两条被监听的 URL，想想列表数据什么时候才"可安全读取"。）
做完后点开核对答案

① 4 处：:952 jobList、:1097 hasMore、:1155 详情 data、:1156 currentJob。

② 两处 waitForResponse：:1139（点卡片后等 job/detail.json，仅 URL 前缀）与 :1572（开聊后等 friend/add.json，额外要求 URL 含 jobId=${targetJobData.jobInfo.encryptId}——因为聊天页可能同时有别的 add 请求，必须锁定是本职位的那一个，和翻页配对同一思想）。

③ 列表 API 响应到达时，Vue 还没把它合并渲染进实例；且翻页是"滚一下发一次"的连续过程，直接消费响应对象要处理乱序。而 __vue__.jobList 是 Vue 已经消化完的状态——框架层取的是"渲染后的真相"，天然免同步问题。本项目其实也监听了列表请求（:914），但只用作翻页时机信号，不取其响应体——两种层次各取所长。
